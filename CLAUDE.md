## Private context vs. public content

`PROJECT_CONTEXT.md` is **development context, not website copy**. Being listed there does not
make information approved for publication.

- Only items marked **Public: Yes** in `PROJECT_CONTEXT.md` may appear on website pages.
- Items marked **Private** or **Pending approval** must never be placed in HTML, image alt
  text, metadata, or any other published file.
- When a task would publish a new personal detail, ask Jordan first, then record the approval
  in `PROJECT_CONTEXT.md` before using it.
- Remember that `PROJECT_CONTEXT.md` itself lives in a public repository: never add sensitive
  personal information to it, even as private context.

## Specification-driven development

- Features go through the Spec Kit flow: `/speckit-specify` → `/speckit-clarify` (as needed)
  → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`.
- Do not write implementation code for a feature until its spec and plan exist and the user
  has approved moving to implementation.
- Every plan's Constitution Check must cite the relevant constitution principles.
- Small fixes (typos, broken links, single-rule CSS corrections) may skip the full flow, but
  still must pass the constitution's quality gates.

## Code standards

- Clean, hand-authored HTML5, CSS3, and vanilla JavaScript. No frameworks, build tools, CDNs,
  or package managers (constitution Principle I).
- Semantic markup and WCAG 2.1 AA accessibility on every page (Principle II).
- Content must work without JavaScript; scripts enhance only (Principle III).
- New styles use existing tokens and components; no inline styles or per-page `<style>` blocks
  (Principle IV).
- Match the surrounding code's formatting, naming, and comment density.
- Update the `?v=` cache-busting query on every page whenever `style.css` or `script.js`
  changes (Principle V).

## Content integrity

  employers, dates, or project evidence.
- When required content is missing, insert a clearly marked placeholder (`[NEEDS INPUT: ...]`)
  and list it for the user rather than writing plausible-sounding copy.
- Draft structure, headings, and prompts freely; personal substance must come from the user.
- Keep sensitive personal information (phone numbers, home address, private identifiers) out
  of the repository. Publish only contact details the user explicitly approves.
